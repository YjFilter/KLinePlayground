# KLinePlayground 多 AI Agent 协作与持续推进设计

## 1. 背景

KLinePlayground 当前是一个以 Flask/PyWebView 为运行入口、原生 HTML/CSS/JavaScript 为前端的 A 股 K 线复盘与模拟交易应用。项目已具备训练、交易、历史报告、用户设置、AI 点评和桌面打包能力，但主要业务仍集中在少数大型文件中：前端主脚本约 3,500 行，Flask 应用约 1,000 行，数据管理模块约 1,200 行。当前工作区还有一轮较大的未提交改动和少量回归测试。

本设计的目标不是开发一个独立的通用 Agent 平台，而是在仓库内建立一套轻量、可版本化、可审查、可跨 AI 产品使用的控制平面，使 Codex 成为主脑，并让 WorkBuddy 等外部 Agent 安全承担普通或简单任务。

## 2. 目标与非目标

### 2.1 目标

- Codex 负责恢复项目上下文、诊断、规划、任务拆解、复杂实现、集成、审查和最终验收。
- WorkBuddy 等外部 Agent 通过标准 Markdown 任务包执行边界清晰、低风险的工作。
- 仓库保存方向、项目记忆、任务状态、架构决策、验收证据和每轮交接，使后续会话不依赖聊天记录。
- 每次由项目所有者主动启动一轮推进，不启用无人监管的持续自治开发。
- 建立测试、CI、构建和发布质量门禁，并逐步模块化现有代码以支持安全并行。

### 2.2 非目标

- 不建设独立 Agent 调度服务、消息队列、Agent 状态数据库或常驻调度器。
- 不允许外部 Agent 自行改变产品路线图、公共接口、持久化格式或核心交易规则。
- 不自动发布版本，不自动删除用户数据，不在未批准时扩大当前里程碑。
- 第一阶段不为追求并行而立即大规模重写业务代码。

## 3. 方案选择

采用“仓库原生控制平面”方案：代码仓库同时承载代码、方向、记忆、任务和证据，是唯一事实源。该方案兼容 Codex、WorkBuddy 和其他能够读写仓库文件的 AI 产品，不绑定厂商专用 Agent API，也避免引入独立编排平台的开发与维护成本。

## 4. 角色与权限

### 4.1 项目所有者

- 启动每轮推进，给出目标或要求 Codex 继续当前路线图。
- 审批范围变化、高风险决策、破坏性迁移和正式发布。
- 决定产品优先级和最终业务取舍。

### 4.2 Codex Orchestrator

- 读取 Git 状态、项目状态、路线图、架构地图、领域规则、任务池和上轮交接。
- 选择当前最有价值且风险可控的工作，生成任务依赖关系和执行顺序。
- 完成复杂、跨模块、上下文密集或高风险任务。
- 为外部 Agent 生成完整任务包并分配明确的文件写入所有权。
- 审查外部 Agent 的代码差异、结果报告和测试证据。
- 运行质量门禁，只有验收通过后才能将任务标记为完成。
- 更新全局状态、路线图、风险、决策记录和下一轮建议。

### 4.3 Worker Agent

- 只执行分配给自己的任务包。
- 只修改任务包列出的文件或目录；其他内容默认只读。
- 不自行扩大任务范围，不修改架构、公共接口和全局计划。
- 提交结构化结果报告，包括变更摘要、测试命令、测试结果、风险和未完成事项。
- 不能自行把任务标记为完成，只能提交到待审查状态。

### 4.4 CI 与质量门禁

CI 是独立证据来源，不接受 Agent 仅凭自然语言声明“已经完成”。任何强制门禁失败时，任务不能进入完成状态，也不能进入发布基线。

## 5. 仓库控制平面

建议增加以下结构：

```text
AGENTS.md
.agent/
  PROJECT.md
  STATE.md
  ROADMAP.md
  ARCHITECTURE.md
  DOMAIN_RULES.md
  QUALITY_GATES.md
  WORKFLOW.md
  decisions/
  tasks/
    backlog/
    ready/
    active/
    review/
    done/
    blocked/
  handoffs/
  templates/
scripts/
  agent_status.py
  quality_gate.py
  project_snapshot.py
.github/workflows/quality.yml
```

### 5.1 方向层

- `PROJECT.md`：产品目标、目标用户、范围、成功指标和明确非目标。
- `ROADMAP.md`：里程碑、优先级、依赖和完成定义。
- `STATE.md`：当前阶段、正在进行的任务、阻塞项、风险和推荐下一步。

### 5.2 记忆层

- `ARCHITECTURE.md`：代码地图、模块职责、入口、关键数据流和外部依赖。
- `DOMAIN_RULES.md`：T+1、涨跌停、交易成本、订单成交、复权和报告统计等不可破坏的领域不变量。
- `decisions/`：使用 ADR 记录重要架构决策、替代方案和后果。

### 5.3 执行层

- `tasks/`：按状态存储任务包。
- `templates/`：任务包、结果报告、验收报告、ADR 和 handoff 模板。
- `WORKFLOW.md`：定义任务流转、文件所有权、交接、返工和阻塞处理规则。

### 5.4 证据层

- `QUALITY_GATES.md`：必须运行的测试、构建、检查和验收要求。
- `handoffs/`：每轮推进结束时的状态快照。
- 任务完成记录：保留测试输出摘要、审查结论和未解决风险。

## 6. 任务生命周期

任务按以下状态流转：

```text
backlog -> ready -> active -> review -> done
                    |          |
                    v          v
                  blocked    ready
```

- `backlog`：方向正确，但上下文或优先级尚未满足执行条件。
- `ready`：目标、边界、依赖、文件所有权和验收标准完整，可直接领取。
- `active`：已分配唯一 owner，写入范围已锁定。
- `review`：执行者已提交结果和证据，等待 Codex 审查。
- `done`：Codex 验收通过且强制质量门禁通过。
- `blocked`：缺少产品决策、外部资源、前置任务或遇到无法在原范围内解决的问题。

任何 Agent 都不能跳过 `review` 直接进入 `done`。审查不通过时退回 `ready` 并补充返工要求。

## 7. 标准任务包

每个可交给外部 Agent 的任务包必须包含：

1. 唯一任务 ID、标题、优先级和当前状态。
2. 背景与业务价值。
3. 明确目标和可观察产出。
4. 非目标与禁止事项。
5. 允许修改的文件或目录。
6. 只读参考文件和必要上下文。
7. 前置任务、依赖和已知风险。
8. 实施约束和不可破坏的不变量。
9. 验收标准。
10. 必须执行的测试、检查或构建命令。
11. 结果报告格式。

同一轮中，一个文件只能有一个写入 owner。多个任务需要修改同一文件时，必须串行执行或先由 Codex 拆出稳定接口。

## 8. 工作分配原则

### 8.1 适合外部 Worker

- 补充独立、明确的测试用例。
- 更新文档、类型说明、数据样例和操作指南。
- 局部样式、小型前端组件或不改变公共接口的 UI 调整。
- 明确接口下的局部重构。
- 重复性维护脚本、格式整理和低风险数据处理。

### 8.2 必须由 Codex 负责

- 跨前后端架构拆分和公共接口设计。
- 交易、资金、持仓、订单和复权等核心规则。
- 持久化格式、用户数据迁移和兼容性策略。
- 多任务集成、冲突解决和回归分析。
- 最终验收、全局状态、路线图、发布基线和回滚策略。

## 9. 每轮推进流程

当项目所有者说“继续推进”或指定目标时，Codex 执行：

1. **恢复**：读取 Git 状态、`STATE.md`、`ROADMAP.md`、当前任务、上轮 handoff 和质量状态。
2. **诊断**：识别阻塞、风险、回归、技术债和当前里程碑的最短推进路径。
3. **规划**：选择一组边界明确、依赖可满足的任务，建立执行顺序和文件所有权。
4. **执行**：Codex 完成复杂任务；为低风险任务生成可复制给外部 Agent 的任务包。
5. **集成**：读取外部 Agent 结果，检查越界修改、接口影响和潜在冲突。
6. **验收**：运行目标测试，再运行适用的完整质量门禁。
7. **收口**：更新任务状态、项目状态、路线图、风险、ADR 和 handoff。
8. **汇报**：向项目所有者说明完成内容、证据、剩余风险和推荐下一步。

## 10. 质量门禁

第一版最低门禁：

- Python 关键模块能够导入。
- `tests/` 中的自动化测试全部通过。
- T+1、涨跌停、费用、订单成交和报告统计具备回归测试。
- 前端 JavaScript 通过语法检查。
- Flask 关键 API 具备接口级测试。
- 应用完成启动冒烟测试。
- 桌面打包流程能够完成或有明确、可重复的人工验证步骤。
- Agent 结果报告包含实际运行的命令和结果，而不是建议用户自行验证。

质量门禁分为必需和条件性两类。文档任务不应被桌面打包阻塞，但核心交易逻辑变更必须运行完整业务规则测试和相关 API 测试。

## 11. 安全边界

- 不自动删除用户数据、历史记录或离线行情数据。
- 不自动提交、推送、合并或发布，除非项目所有者明确要求。
- 不把 API Key、个人数据或机器路径写入版本库。
- 不允许 Worker 修改未声明文件；发现需要越界时进入 `blocked`。
- 不允许在无迁移和回滚设计的情况下更改持久化格式。
- 不允许核心交易规则仅依赖 UI 或端到端测试，必须具备领域级单元测试。

## 12. 分阶段落地

### M0：稳定当前基线

- 审查当前未提交改动，确认完成范围和剩余问题。
- 运行现有测试并记录基线结果。
- 固定依赖、启动、测试和打包命令。
- 完善忽略规则并排除临时生成物和敏感配置。
- 在基线稳定前，不并行分派业务代码任务。

### M1：建立 Agent 控制平面

- 创建 `AGENTS.md`、`.agent/` 文件和模板。
- 填充项目目标、架构地图、领域规则、路线图和当前状态。
- 添加任务状态检查、项目快照和统一质量门禁脚本。
- 创建第一份真实 handoff 和首批任务包。

### M2：建立 CI 与工程门禁

- 扩充核心业务回归测试和 Flask API 测试。
- 增加前端语法检查、应用启动冒烟测试和构建检查。
- 配置 GitHub Actions 质量工作流。
- 定义版本、发布、回滚和发布说明流程。

### M3：模块化以支持并行

- 拆分 `frontend/js/main_enhanced.js` 为状态、API、图表、训练、交易、报告、用户和设置模块。
- 拆分 `backend/app_enhanced.py` 为 Blueprint、应用服务和领域服务。
- 拆分 `backend/data_manager.py` 为数据源、缓存、同步和行情仓储。
- 稳定前后端数据契约，并将核心交易规则从路由和 UI 中分离。

### M4：持续产品推进

- 每次由项目所有者主动启动一轮推进。
- Codex 自动恢复上下文、选择当前里程碑任务并判断执行者。
- 外部 Agent 根据标准任务包完成低风险工作。
- Codex 负责集成、验收、状态更新和下一轮建议。

## 13. 成功标准

- 新 Codex 会话只读取仓库文件即可说明当前目标、状态、风险和下一步。
- 外部 Agent 无需阅读整个代码库即可完成一个 `ready` 任务。
- 任一任务都能追溯 owner、写入范围、变更、测试证据和验收结论。
- 多 Agent 同一轮工作时不存在未声明的文件写入冲突。
- 核心交易规则变更能够被自动化回归测试保护。
- 项目所有者只需发出“继续推进”，Codex 就能提出并执行下一组合理工作。

## 14. 首次实施顺序

1. 保护并审查当前未提交改动。
2. 建立 M0 基线报告。
3. 创建控制平面目录、规范和模板。
4. 生成当前架构地图和领域规则清单。
5. 建立统一质量门禁入口。
6. 创建第一批任务包，其中低风险任务用于验证 WorkBuddy 交接流程。
7. 完成一次真实的执行、审查、返工或验收闭环。
